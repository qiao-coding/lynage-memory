# 工作原理

> 从消息到窗口到阶段到搜索到结论——完整管道。

---

## 总览：数据怎么流动

```
用户说话
  │
  ▼
startTurn() ──→ 消息写入数据库 (追加，不修改)
  │
  ▼
streamText() ──→ LLM 回复
  │
  ▼
finishTurn() ──→ 保存回复 ──→ 检查: 当前对话 Token 是否超标?
                                    │
                         ┌──────────┴──────────┐
                         │ 未超标               │ 超标
                         ▼                     ▼
                      继续对话           归档: 旧对话 → 冻结成窗口
                                              │
                                        AI 读窗口原文 → 生成标签
                                        (summary + keywords)
                                              │
                                        窗口加入阶段
                                              │
                                        阶段满了?
                                    ┌─────┴─────┐
                                    │ 没满        │ 满了
                                    ▼             ▼
                                 继续          升代: 创建上层阶段
                                              AI 读子阶段标签 → 生成概述
```

---

## 第一步：消息存储 (Event Sourcing)

每一条消息是一个不可变事件。追加写入，从不修改。

```
messages 表:
┌────────┬──────┬─────────────────────┬──────────────┐
│ id     │ role │ content             │ createdAt    │
├────────┼──────┼─────────────────────┼──────────────┤
│ msg-1  │ user │ 我要做组件库...      │ 7/25 09:00   │
│ msg-2  │ asst │ 建议用 TS + Vite... │ 7/25 09:01   │
│ msg-3  │ user │ CSS Modules 怎么样? │ 7/25 09:02   │
│ ...    │ ...  │ ...                 │ ...          │
└────────┴──────┴─────────────────────┴──────────────┘

永远不会出现: UPDATE messages SET content = '...' WHERE id = 'msg-3'
只有: INSERT INTO messages VALUES (...)
```

## 第二步：归档 — 旧对话冻结成窗口

当当前对话的 Token 数超过阈值：

```
  ① 找自然边界: 不能切断 Q&A 对、不能切断 Tool 调用/结果
        │
  ② 把旧消息冻结成窗口
        窗口 = { msg-1, msg-2, ..., msg-84 }
        │
  ③ AI 读全部原文 → 生成标签
        │
        输入 (AI 看到的):           输出 (AI 生成的):
        ┌──────────────────┐       ┌─────────────────────────┐
        │ [USER] 我要做...   │       │ summary: "讨论技术选型，  │
        │ [ASST] 建议用...   │  →    │   确定 CSS + TS + Vite" │
        │ [USER] CSS 怎么样? │       │ progress: "技术选型完成" │
        │ ...               │       │ keywords: [CSS, TS,     │
        │ (共84条)           │       │   Vite, 组件库]         │
        └──────────────────┘       └─────────────────────────┘
        │
  ④ 标签存入窗口记录。原文在消息表中不动。
        窗口.sourceFrom = msg-1    ← 指针: 从这里
        窗口.sourceTo   = msg-84   ← 指针: 到这里
```

**标签只是导航工具。原文在消息表中一字不差。**

---

## 第三步：升代 — 窗口太多时建阶段

一个阶段下窗口数达到上限 (默认 20)：

```
之前:                            之后:
  📁 (20 个窗口平铺)               📁 阶段: 前期开发
                                     │ AI 读 20 个窗口的标签 → 生成:
                                     │ overallContent: "从技术选型开始,
                                     │   经历组件开发, 完成样式迁移"
                                     │ mainConclusions: [Tailwind, TS]
                                     │ importantChanges: [CSS→Tailwind]
                                     │
                                     └── 📁 (20 个窗口, 降级为子节点)
```

**升代时 AI 只读标签，不读原文。** 原文只在搜索验证时才被打开。

为什么这样做：读 20 段标签 ~500 tokens，读 20 个窗口的原文 ~10000 tokens。升代很快，但代价是上层概述可能不够精确——所以搜索时必须回到原文验证。

继续升代：G1 又满 → G2。G2 的概述基于 G1 的标签生成。

```
  📁 G2: "组件库项目从零到完整"
    ├── 📁 G1: "前期开发" (基于 20 个窗口标签生成)
    └── 📁 G1: "架构重构" (基于 20 个窗口标签生成)
```

---

## 第四步：搜索 — 找到相关窗口

用户问历史问题，怎么找到相关窗口？

```
lynageSearch("为什么不用 CSS Modules 了？")
  │
  ├─ 路径 A: FTS5 全文搜索
  │     在所有消息原文 + 窗口标签中搜 "CSS Modules"
  │     → 找到 msg-40, msg-76, msg-82 匹配
  │     → 定位这些消息属于窗口 #1 和窗口 #3
  │
  ├─ 路径 B: 阶段树逐层匹配
  │     Root → G1 "前期开发" → 窗口 #1 标签匹配 → 窗口 #3 标签匹配
  │
  └─ 合并结果: 窗口 #1 (相关性 0.5), 窗口 #3 (相关性 0.9)
```

---

## 第五步：原文验证 — 确认标签说的是真的

搜索结果不能直接当结论——必须打开原文验证。

```
SourceVerifier.verify(窗口 #3, "CSS Modules")
  │
  ├─ 打开窗口 #3 的原文: msg-73 ~ msg-79
  │
  ├─ 检查 query 关键词在原文中的出现情况:
  │     "CSS Modules" 出现 4 次
  │     "不用了" / "切换" / "替代" 出现 3 次
  │     → 匹配度: 高
  │
  ├─ 计算置信度: 0.9
  │
  └─ 返回: { verified: true, confidence: 0.9, actualContent: "msg-73: hover不好调..." }
```

**置信度低的候选被过滤掉，不返回给 LLM。**

---

## 第六步：得出结论 + 写回

```
LLM 收到:
  ① 用户问题: "为什么不用 CSS Modules 了？"
  ② 验证过的原文:
     msg-73 [user] "Button hover 效果怎么这么难调？"
     msg-74 [asst] "CSS Modules 不支持动态样式..."
     msg-75 [user] "有没有更好的方案？"
     msg-76 [asst] "Tailwind 可以做动态样式，但需要迁移"
     msg-77 [user] "迁移要多久？"
     msg-78 [asst] "约 3-4 天"
     msg-79 [user] "那就切吧"
  ③ 当前工作记忆

LLM 回复:
  "在第 73~79 轮讨论中，因为 CSS Modules 不支持动态样式，
   导致 hover 效果难以调整。评估后发现 Tailwind 可以解决，
   迁移成本约 3-4 天，于是决定切换。"

LLM 附带写回操作:
  memoryActions: [
    { target: "workingMemory", operation: "append",
      section: "confirmed",
      value: "CSS→Tailwind 因为动态样式需求" }
  ]
        │
        ▼
  校验: Zod Schema → Lynage 语义 (不能覆盖原文, 不能推测当事实)
        │
        ▼
  写入工作记忆
```

---

## 并行搜索: 多个 Worker 同时找

重要问题需要翻遍全部窗口时：

```
主进程创建项目快照 (在找什么、已经知道什么)
  │
  ├── Worker A: 读阶段 A → 返回证据位置
  ├── Worker B: 读阶段 B → 返回证据位置
  ├── Worker C: 读阶段 C → 返回证据位置
  └── Worker D: 读阶段 D → 返回证据位置
  │
  ▼
主进程: 合并去重 → 原文验证 → 演变链重建 → 输出结论

Worker 只返回证据位置。不修改记忆。不生成最终答案。
```

---

## 总结

```
消息 (原文，永不丢失)
  │
  ├─ 归档 → 窗口 (标签 + 原文指针)
  │           │
  │           └─ 升代 → 阶段 (标签嵌套)
  │
  ├─ 搜索 → 在所有窗口标签中匹配
  │           │
  │           └─ 原文验证 → 打开原文确认
  │                          │
  │                          └─ 写回 → 确认的结论写入工作记忆
  │
  └─ 编译 → 筛选相关内容 → LLM 看到的精简文本
```

**标签是工具，原文是事实。标签写错了没关系，打开原文就清楚了。**
