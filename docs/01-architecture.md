# Lynage Memory 架构详解

## 核心思想

```
传统方案：  消息 → 太多了 → 压缩成摘要 → 原文丢弃 ❌
Lynage：   消息 → 太多了 → 原文归档 → 只给摘要做导航 → 需要时找回原文 ✅
```

## 全景数据流

```
   用户输入 ──────────→  lynageStreamText()
                         │
                         ├─ ① startTurn()  ──→ 保存 user 消息
                         ├─ ② streamText() ──→ 调用 LLM
                         └─ ③ finishTurn() ──→ 保存 assistant 消息
                              │
                              └─ 检查: 活跃窗口是否超出 Token 阈值?
                                   │
                                   ├─ 未超出 → 继续
                                   └─ 超出 → 冻结旧对话为上下文窗口 (Chunk)
                                               └─ 加入目录树
                                               └─ 目录满 → 窗口套窗口 (升代)

              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
        ┌──────────┐    ┌──────────────┐   ┌──────────────┐
        │ Messages │    │ Context      │   │  Directories │
        │  (原文)   │    │ Chunks       │   │  (窗口目录)   │
        │          │    │ (冻结的窗口)   │   │              │
        │  msg-1   │    │ 🗂 窗口 #1    │   │ 📁 G0 → 🗂   │
        │  msg-2   │    │ 🗂 窗口 #2    │   │ 📁 G1 → 📁   │
        │  ...     │    │ 🗂 窗口 #3    │   │ 📁 G2 → ...  │
        └──────────┘    └──────────────┘   └──────────────┘

              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
        ┌────────────┐                     ┌────────────┐
        │  Working   │                     │    User    │
        │  Memory    │                     │   Memory   │
        │ (项目便签)  │                     │ (用户画像)  │
        └────────────┘                     └────────────┘
              │                                   │
              └───────────────┬───────────────────┘
                              ▼
                    ┌──────────────────┐
                    │ Context Compiler │──→ LLM 看到的精简文本
                    └──────────────────┘
```

---

## 七层结构（自底向上）

```
  Layer 7  Context Compiler    给模型看的"精简视图"
  Layer 6  User Memory         长期不变的"用户画像"
  Layer 5  Working Memory      Agent 的"便签纸"
  Layer 4  Generations         子上下文分组（阶段→子阶段）
  Layer 3  Directories         工作区上下文（父类）
  Layer 2  Context Chunks      子类上下文（冻结的对话窗口）
  Layer 1  Messages            原文地基（永不丢失）
```

### 父子关系

```
工作区上下文 (父类)            = Directory / 项目
  ├── 阶段 (子类上下文)        = Directory (嵌套)
  │     └── 冻结窗口 (子类)    = Context Chunk
  └── 当前活跃对话             = Recent Messages
```

---

## Layer 1：Messages — 永不丢失的原文

这是最底层。用户看到的是「上下文窗口」，系统内部每条消息是一条记录。

```
用户视角:   🗂 窗口 #1 (第 1~42 轮: 技术选型)
系统内部:   msg-1  "我要做组件库..."
           msg-2  "建议用 TypeScript..."
           msg-3  "CSS Modules 怎么样？"
           ...
           msg-84 "好的，开始迁移 Tailwind"

窗口只是"框"——框住了 msg-1 到 msg-84 这段范围。
原文在 messages 表中，每条追加写入，从不修改、从不删除。
```

```
┌──────────────────────────────────────────────────┐
│ messages 表                                       │
├────────┬──────────┬─────────┬────────────────────┤
│ id     │ role     │ content │ createdAt          │
├────────┼──────────┼─────────┼────────────────────┤
│ msg-1  │ user     │ 你好     │ 2026-07-25 09:00  │
│ msg-2  │ assistant│ 你好！   │ 2026-07-25 09:01  │
│ msg-3  │ user     │ 帮我...  │ 2026-07-25 09:02  │
│ ...    │ ...      │ ...     │ ...                │
│ msg-N  │ ...      │ ...     │ ...                │
└────────┴──────────┴─────────┴────────────────────┘
```

**关键字段**：`sourceFromId` / `sourceToId` 形成精确定位链，确保可以找回任意一段原文。

---

## Layer 2：Context Chunk — 子类上下文（冻结的对话窗口）

当活跃对话超过 Token 阈值，旧对话被「冻结」成工作区下的一个子类上下文。

```
        活跃窗口太大（> 16K tokens）
              │
              ▼
    ┌─────────────────────┐
    │ 找自然边界            │  不能切断 Q&A 对
    │ (boundary-detector) │  不能切断 Tool调用/结果
    └────────┬────────────┘
              │
              ▼
    ┌─────────────────────┐
    │ 旧对话 → 冻结成窗口    │
    │ AI 生成窗口摘要标签    │
    └────────┬────────────┘
              │
              ▼
    ┌──────────────────────────────────────────────┐
    │ 上下文窗口 #028                               │
    ├──────────────────────────────────────────────┤
    │ 摘要:    "讨论数据库方案，决定用 SQLite"        │
    │ 关键词:   [SQLite, WAL, Drizzle]              │
    │ 内容范围: 第 42~55 轮对话                      │
    │ 原文:     ✅ 已保存，随时可打开阅读              │
    └──────────────────────────────────────────────┘
```

**用户看到的是上下文窗口。系统内部用 msg ID 精确定位原文。**

## Layer 3：Directory — 工作区上下文（父类）

```
子上下文 #1
子上下文 #2     }──→  太多了，建个工作区目录
子上下文 #3
子上下文 #4
子上下文 #5

变成:

    📁 工作区: React 组件库开发 (父类上下文)
    ├── 🗂 子上下文 #1: 技术选型
    ├── 🗂 子上下文 #2: 初期开发
    ├── 🗂 子上下文 #3: 样式迁移
    ├── 🗂 子上下文 #4: 重构
    └── 🗂 子上下文 #5: 新功能
```

**工作区 = 父类上下文，管理它的所有子上下文。** 记录了这段时间项目推进了什么、形成了什么结论。

---

## Layer 4：代际压缩 — 子上下文分组

子上下文太多 → 创建「阶段」来分组。阶段本身也是子类上下文（可以继续嵌套）。

```
之前：                         之后：
  📁 工作区                     📁 工作区
  └── 📁 (20 个子上下文)         ├── 📁 阶段: 前期开发 (新的子类上下文)
                                │     摘要: "架构设计阶段"
                                │     └── 📁 (20 个子上下文，降级)
                                └── (新子上下文继续往这里加)

再归档 → 又装满 20 个 → 再分组：

  📁 工作区: React 组件库开发
  ├── 📁 阶段: 前期开发 (第 1~120 轮)
  │     摘要: "架构设计、组件开发和样式迁移"
  │     └── 20 个子上下文
  └── 📁 阶段: 架构重构 (第 121~180 轮)
        摘要: "monorepo 重构、团队扩展"
        └── 20 个子上下文
```

**父类上下文包含子类上下文，子类可以继续嵌套。每个子上下文都可以展开看到原文。**

---

## Layer 5：Working Memory — Agent 的便签纸

记录"现在做到哪了"，每轮对话自动注入。

```
┌─────────────────────────────────┐
│ Working Memory                  │
├─────────────────────────────────┤
│ currentTask    设计数据库方案     │
│ confirmed      SQLite + WAL     │
│ confirmed      Drizzle ORM      │
│ progress       已确定存储方案     │
│ unresolved     阈值设为多少？     │
└─────────────────────────────────┘
         │
         ▼  每次调用 LLM 时自动注入
    "# Working Memory
     Current Task: 设计数据库方案
     Confirmed: SQLite + WAL, Drizzle ORM
     ..."
```

---

## Layer 6：User Memory — 长期不变的用户画像

跨任务、跨会话的稳定信息。

```
┌─────────────────────────────────┐
│ User Memory (user-001)          │
├─────────────────────────────────┤
│ preferences    回答简洁直接       │
│ preferences    技术判断严谨       │
│ constraints    不用向量数据库     │
│ constraints    不绑定特定厂商     │
│ background     7年全栈开发       │
└─────────────────────────────────┘
```

**和 Working Memory 的区别**：User Memory 很少变（用户偏好、长期约束），Working Memory 每轮都可能变（当前进度、未决问题）。

---

## Layer 7：Context Compiler — 编译给模型看的视图

6 种场景，编译不同内容：

```
场景                 编译内容
──────────────────────────────────────────
normal-chat         User + Working + Recent Messages
project-work        加上 Directory 摘要 + 未解决问题
history-search      验证后的候选原文 + 置信度
source-verification 候选原文全文 + query 对照
archive-indexing    Chunk 原文 → 摘要 Prompt
worker-search       项目快照 + 子目录（并行搜索用）
```

## 搜索流程

```
lynageSearch("为什么放弃语义分类？")
        │
        ├─ ① FTS5 搜所有窗口摘要 + 原文 → 找到匹配窗口
        ├─ ② 目录下钻 Root → G1 → G0 → 窗口 #028
        ├─ ③ 打开窗口 #028，验证原文是否真的匹配 → 置信度 85%
        └─ ④ 把窗口内容编译进当前 LLM 上下文
```

**用户看到：在所有历史窗口中搜索 → 找到 → 打开阅读。**

**模糊搜索**：创建 SearchTask → 分批检查目录 → 保存游标 → 跨轮次继续。

**并行搜索**：主进程创建快照 → N 个 Worker 并发读不同目录 → 合并去重 → 原文验证 → 演变链重建。

```
AI 回复附带 memoryActions
        │
        ▼
  ① JSON 解析
  ② Zod Schema 校验（target/operation/section/value）
  ③ Lynage 语义校验（不能覆盖原文、不能删目录、不能推测当事实）
  ④ 数据库事务写入
        │
        ├─ target="workingMemory" → working_memory 表
        └─ target="userMemory"    → user_memory 表
```
